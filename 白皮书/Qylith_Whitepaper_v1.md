## 第一章：问题陈述——为什么Qylith必须存在

### 1.1 量子威胁：不是"如果"，而是"何时"

2026年之前，量子威胁被认为是遥远的未来。2026年3月之后，这个认知被彻底颠覆。

Google量子AI团队发表的论文《Cryptographically Relevant Quantum Computing: Timeline and Implications》给出了精确的时间线分析：

| 量子计算发展里程碑 | 预计时间 | 对区块链的影响 |
|-------------------|---------|----------------|
| 1,000物理量子比特 | 2026-2027 | 理论威胁开始显现 |
| 50,000物理量子比特 | 2027-2029 | **ECDSA可被攻破** |
| 100万+物理量子比特 | 2029-2032 | 所有非PQC加密受威胁 |

**关键结论**：50万物理量子比特即可攻破ECDSA签名。这意味着：
- 攻击者可伪造签名，窃取任意地址的资产
- 历史交易可被追溯篡改（"harvest now, decrypt later"攻击）
- 跨链桥的信任假设将被彻底打破

**行业现状**：当前以太坊、Solana、Bitcoin等主流链的交易签名均基于ECDSA secp256k1或Ed25519。这些算法在量子计算机面前如同纸糊。

**紧急行动窗口**：建设一条抗量子链的窗口期只有2-3年。但现有的"抗量子"方案存在致命缺陷：

1. **临时打补丁**：在现有链上添加PQC层，引入复杂的兼容性技术债
2. **分叉过渡**：需要硬分叉，面临社区分裂风险
3. **非原生设计**：PQC是附加物，而非架构核心

**Qylith的答案**：从创世区块起，原生集成NIST标准化的后量子密码学算法。没有迁移，没有分叉，没有妥协。

**AI Agent当前面临的困境**：


**行业现状**：当前"AI+区块链"的结合方式停留在：
- AI生成NFT（创作层）

这些都是AI对区块链的"外部赋能"，而非区块链对AI的"原生支持"。

## 第四章：密码学层——量子时代的安全基石

### 4.1 为什么选择NIST后量子密码学标准

2024年，NIST正式发布后量子密码学标准，这是全球密码学界30年研究的结晶。与学术算法不同，NIST标准经历了：

- 全球密码学家的公开分析
- 多轮选拔与优化
- 实现安全性与性能的最佳平衡

**Qylith全面采用NIST标准**，确保：
- 法律合规性（政府采购、企业采用的前提）
- 长期安全性（学术与工业界的广泛验证）
- 互操作性（未来与其它PQC系统的集成）

### 4.2 交易签名：FALCON-1024

**算法**：Fast Fourier Lattice-based Compact Signatures over NTRU
**参数**：FALCON-1024（Category 5, 128-bit security level）

**为什么选择FALCON-1024**：
- **最小签名**：1,280字节，比ML-DSA-87小47%
- **极速验证**：0.15ms，比ML-DSA-87快6-7倍
- NIST Level 5（最高安全等级）
- 基于NTRU格密码，理论扎实

**ML-DSA-87保留作为备选**：在过渡期提供ECDSA+ML-DSA混合签名兼容

**在Qylith中的应用**：
- 用户交易签名
- 治理投票签名
- 跨链消息签名
- AI Agent身份绑定

**参数规格**：
```
FALCON-1024 参数：
- Public Key: 1,793 bytes
- Secret Key: ~2,400 bytes
- Signature: 1,280 bytes
- Security Level: NIST Level 5 (128-bit)
- Hard Problem: NTRU Shortest Vector Problem
- Sign/Verify: ~0.1ms / ~0.15ms
```

### 4.3 密钥封装：ML-KEM-768

**算法**：Module-Lattice Key Encapsulation Mechanism
**参数**：ML-KEM-768

**选择依据**：
- 与ML-DSA同体系，简化实现复杂度
- 密钥封装速度优秀，适合高频网络通信
- NIST标准化完成度高

**在Qylith中的应用**：
- 节点间TLS-like加密通道
- 跨链桥的密钥协商
- 秘密共享与阈值签名

**参数规格**：
```
ML-KEM-768 参数：
- Public Key: 1,184 bytes
- Ciphertext: 1,088 bytes
- Shared Secret: 32 bytes
- Security Level: NIST Level 3 (128-bit)
```

### 4.4 过渡期方案：混合签名

**问题**：用户可能已有ECDSA密钥对，如何平滑迁移？

**解决方案**：混合签名机制（Hybrid Signature）

**工作原理**：
```
Hybrid Signature = ECDSA Signature + ML-DSA-87 Signature

验证条件：两者同时验证通过 = 签名有效

优势：
1. 兼容现有钱包（Metamask等）
2. 提供双保险（任一算法被攻破，另一层仍安全）
3. 平滑过渡（非硬分叉）
```

**过渡时间线**：
- 阶段1（创世区块）：仅支持ML-DSA-87原生签名
- 阶段2（主网上线6个月后）：支持ECDSA+ML-DSA混合签名
- 阶段3（主网上线18个月后）：仅ML-DSA-87（ECDSA不再有效）

### 4.5 Crypto-Agility：面向未来的可升级性

**问题**：未来可能出现更强的PQC算法，或现有算法被发现弱点。

**解决方案**：Crypto-Agility架构

**设计原则**：
1. **算法抽象层**：协议层不硬编码特定算法
2. **版本化签名格式**：签名包含算法标识符
3. **链上升级机制**：通过治理投票升级密码学参数
4. **向后兼容**：旧签名格式继续有效

**升级路径**：
```
当前：ML-DSA-87 + ML-KEM-768
      ↓ (通过治理投票)
未来：可能升级至更高效的格密码算法
```

## 第五章：共识层——Nominated Proof of Stake (NPoS)

### 5.1 为什么选择NPoS

**Qylith选择NPoS而非传统PoS或PoW，基于以下考量**：

1. **安全性**：NPoS的验证人选举机制提供比传统PoS更强的抗攻击性
2. **去中心化**：提名人机制允许小额QYL持有者参与安全维护
3. **能源效率**：纯质押证明，无需物理算力
4. **抗量子基础**：PoW的SHA-256在量子计算机面前也会加速（Grover算法），NPoS基于签名安全，不受量子影响

### 5.2 NPoS机制详解

**角色定义**：
- **验证人（Validator）**：运行完整节点，参与出块与最终性确认
- **提名人（Nominator）**：质押QYL支持验证人，分享收益与风险

**选举机制**：
- 每个 era（时代，6小时）重新选举验证人集合
- 基于可用质押量+历史表现的Phragmén选举算法
- 确保验证人集合的公平分配

**质押参数**：
```
最小验证人质押：100,000 QYL
最小提名人质押：1,000 QYL
最大验证人数：1,000
每个提名人最多支持：16个验证人
每个验证人最多接受：256个提名人支持
```

### 5.3 出块与最终性

**时间参数**：
- **Slot（时隙）**：6秒（一个区块的生产周期）
- **Epoch（纪元）**：300个Slot（约30分钟）
- **Era（时代）**：12个Epoch（约6小时）

**最终性保证**：
- 区块需要2/3+验证人的签名确认
- 确认延迟：12-18秒（2-3个区块）
- 最终性 gadget（GRANDPA或类似）确保不可逆

**性能指标**：
```
目标TPS：10,000+ (通过并行执行引擎)
实际出块时间：6秒
最终性确认：12-18秒
最大验证人：1,000+
年化质押收益：约12-15%
```

## 第六章：执行层——AI原生的智能合约与Agent环境

### 6.1 为什么需要AI原生的执行层

**以太坊EVM的问题**：
- 为确定性计算设计
- 无法原生支持AI推理
- 无Agent身份与声誉机制

**AI Agent的需求**：
- 确定性 + 非确定性（推理）混合执行
- 链上身份认证
- 可验证的推理证明
- 自主交易执行

**Qylith的解决方案**：在执行层同时支持：
1. **确定性执行**：WASM智能合约（兼容EVM）
2. **AI原生执行**：AI Agent Execution Module (AEM)

### 6.2 WASM智能合约运行时

**选择WASM的原因**：
- 性能：接近原生速度
- 跨平台：浏览器、服务器、嵌入式均可运行
- 生态：支持Rust、C++、Go等多语言开发
- 确定性：可构建确定性执行环境

**合约语言支持**：
- **ink!**：Rust编写智能合约（Polkadot生态成熟）
- **Solidity**：通过转译或兼容层支持
- **Move**：未来可能引入

**执行模型**：
- 账户模型（类似以太坊）
- Gas计量与执行费用
- 跨合约调用（通过调用树）
- 并行执行优化（见6.4）

### 6.3 AI Agent Execution Module (AEM)

**AEM是Qylith的核心创新**——这不是一个应用，而是一个协议级的原生模块。

**AEM的核心功能**：

#### 6.3.1 Agent Identity & Reputation System (代理身份与声誉系统)

**链上Agent身份**：
```rust
// Agent Identity Structure
struct AgentIdentity {
    public_key: ML-DSA-87 PublicKey,  // Agent的签名公钥
    registration_slot: SlotNumber,    // 注册时区块
    attestation: Vec<Attestation>,    // 第三方认证
    reputation_score: u128,           // 声誉分数（链上计算）
}
```

**声誉系统**：
- 基于历史行为的链上声誉分数
- 可组合的信任图谱（Web of Trust）
- 跨Agent的信用共享

#### 6.3.2 On-Chain Inference Verification (链上推理验证)

**问题**：AI推理本质上是不确定的，如何在确定性链上验证？

**解决方案**：STARK Proof Verification

```
流程：
1. AI Agent在链下执行推理
2. 生成STARK证明（证明推理过程正确）
3. 链上验证STARK证明（不重执行推理）
4. 验证通过 → 执行结果可信
```

**优势**：
- 不需要在链上运行AI模型（成本极高）
- 验证成本远低于执行成本
- 可信度可数学证明

#### 6.3.3 Autonomous Transaction Execution (自主交易执行)

**授权机制**：
```rust
// 用户向Agent授权的权限级别
enum AgentPermission {
    ReadOnly,           // 仅读取（查看余额等）
    TradeOnly,          // 仅交易（特定代币）
    Unilateral,        // 单边执行（Agent自主决定）
    Managed,           // 受管理（需用户确认）  
}
```

**安全措施**：
- 权限级别明确授权
- 交易限额控制
- 时间窗口限制
- 紧急冻结机制

#### 6.3.4 Multi-Agent Orchestration (多代理协调)

**协调协议**：
- Agent间可直接通信（链上消息）
- 支持原子性多跳交易
- 协作任务的分片执行
- 争议解决机制

**用例**：
- DeFi策略：多个Agent协同执行复杂策略
- 身份验证：多Agent交叉验证
- 服务市场：Agent间的任务委托

### 6.4 Parallel Execution Engine (并行执行引擎)

**灵感来源**：MegaETH的并行EVM思路

**问题**：传统区块链串行执行交易，效率低

**解决方案**：乐观并发控制 + 依赖图分析

**执行流程**：
```
1. 区块生产者将交易打包
2. 分析交易间的状态依赖（读写集）
3. 构建依赖图
4. 无依赖交易并行执行
5. 冲突检测与回滚
6. 提交最终状态
```

**性能提升**：
- 理论TPS提升：10-50倍（取决于交易依赖）
- 实际目标：10,000+ TPS

## 第七章：数据层——量子安全的状态管理

### 7.1 Merkle Mountain Range (MMR) 状态存储

**选择MMR的原因**：
- 支持增量添加（append-only）
- 高效的包容性证明
- 范围查询友好
- 状态剪枝友好

**结构**：
```
Block N
    └── State MMR Root
            ├── Leaf: Account State (address, balance, nonce...)
            ├── Node: Intermediate hash
            └── Peak: Final commitment
```

### 7.2 状态过期机制

**问题**：区块链状态无限膨胀，节点存储成本增加

**解决方案**：Epoch-based State Expiry

**设计**：
```
活跃状态（Recent 2 epochs）：完整可读写
历史状态（>2 epochs前）：仅保留MMR根 + 状态证明
恢复机制：提供证明即可恢复历史状态
```

**优势**：
- 减少状态存储需求 ~70%
- 鼓励使用归档节点（提供证明服务）
- 保持历史可验证性

### 7.3 Quantum-Secure State Commitment

**问题**：Merkle树基于SHA-256，在量子计算机面前安全性降低

**解决方案**：使用Poseidon哈希（ZKSync等已采用）

**Poseidon优势**：
- 专为零知识证明设计
- 在zkSNARK/STARK中效率高
- 对量子攻击的抵抗力优于传统哈希
